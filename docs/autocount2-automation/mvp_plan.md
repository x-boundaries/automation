# AutoCount 2.0 Automation MVP Plan

This plan phases the work from API discovery to dashboards and AI summaries. It keeps all production AutoCount automation read-only until the reporting foundation is stable.

The current scope focus is the
[inventory intelligence foundation](inventory_intelligence_scope.md): read-only
inventory, PO, stock movement, and purchasing analytics. CoA, GL, bank opening,
and full accounting cutover work are parked unless a separate finance-owned
scope approves them later.

## Phase 0 - API Discovery

Goal: confirm the safest read path before writing production automation.

Tasks:

- Record installed AutoCount Accounting version/build.
- Confirm SQL Server instance name, database name, and edition.
- Confirm whether the AutoCount API Module is licensed.
- Confirm whether AOTG or API Maintenance is included in the current subscription.
- Run the [AutoCount SQL Server local probe](../autocount_sql_probe.md) on the Windows VM with the read-only login to inventory visible schemas, tables/views, columns, permissions, and heuristic candidate read surfaces.
- Map official AutoCount docs and local sandbox tests to the stock, sales, AR/AP, GL, and item master read surfaces that are safe to use.
- Identify which datasets must use official API/report logic because direct SQL could miss business rules.
- Create a sandbox/test account book if possible.

Deliverables:

- API decision log.
- Confirmed package version to pin.
- SQL probe candidate report, kept outside the repo except for safe summaries.
- [Extraction surface decision pack](extraction_surface_decision.md) using only safe probe summaries.
- Approved read-only source list.
- Initial field/data dictionary for phase 1.

Exit gate:

- A read-only source path is confirmed for at least one dataset.
- No direct production table write path is approved or implemented.

## Phase 1 - Read-only Extractor Skeleton

Goal: create a local scheduled runner that proves safe, repeatable extraction.

Implementation:

- Build a .NET Framework 4.8 console extractor.
- Use config loaded from a local file outside the repo or environment variables.
- Support `--dry-run`, `--business-date`, `--dataset`, and `--output-root`.
- Write a `run_manifest.json` for every run.
- Start with one or two low-risk datasets:
  - item master,
  - debtor/creditor listing,
  - stock status if API/report access is confirmed.
- Use the [Phase 1 extraction mapping](phase1_extraction_mapping.md) and
  [reconciliation checklist](reconciliation_checklist.md) before replacing
  placeholder stock extractor sources.
- Log row counts, start/end time, source version, and exception details.
- Register with Windows Task Scheduler only after manual runs succeed.

Validation:

- Run twice for the same business date and confirm idempotent output.
- Confirm the source login cannot write to AutoCount.
- Confirm no raw extract is written into the Git repo.

Exit gate:

- Daily read-only extractor runs successfully for one week.
- Operations can inspect run status and row counts.

## Phase 2 - Reporting Database Schema

Goal: create a separate analytics store that dashboards and AI can safely consume.

Implementation:

- Create reporting database, for example `XB_AutoCount_Reporting`.
- Create schemas:
  - `raw`,
  - `stg`,
  - `mart`,
  - `audit`.
- Create core audit tables:
  - `audit.extract_run`,
  - `audit.extract_dataset`,
  - `audit.extract_file`,
  - `audit.data_quality_issue`.
- Create first raw/staging/mart tables for selected datasets.
- Add checks for duplicate keys, missing item codes, missing UOM, invalid location, and row-count drift.

Validation:

- Compare row counts against AutoCount UI/report totals for the same date.
- Reconcile stock status totals against an AutoCount stock status/report export.
- Confirm reporting DB writes do not touch the production AutoCount database.

Exit gate:

- First mart views are trusted enough for internal dashboards.

## Phase 3 - Dashboards

Goal: give the team a practical view of sales, stock, master data quality, and extraction health.

Implementation options:

- Power BI Desktop connected to `mart` views.
- Static HTML/Markdown dashboard generated by Task Scheduler.
- Local static dashboard output stored outside this repository.

Initial dashboard pages:

- extraction health,
- product master completeness,
- stock on hand and low stock,
- sales trend by day/channel/outlet,
- open AR/AP summary,
- data quality exception queue.

Validation:

- Reconcile dashboard totals with AutoCount reports.
- Add a visible "last refreshed" timestamp.
- Keep dashboard readers on `mart` views only.

Exit gate:

- Users can answer daily stock/sales questions without opening raw exports.

## Phase 4 - AI Summary Job

Goal: produce a daily management summary from curated reporting views.

Implementation:

- Generate `daily_summary_pack.json` or Markdown from `mart` views.
- Exclude raw customer/supplier rows unless specifically approved and aggregated.
- Send only the summary pack to the AI provider.
- Store prompt version, input pack hash, model/provider, and output hash in `audit.ai_summary_run`.
- Produce a daily Markdown summary with:
  - sales highlights,
  - stock risks,
  - master data issues,
  - AR/AP changes,
  - extractor failures,
  - recommended human follow-up.

Provider choices:

- Local model first if quality and VM resources are acceptable.
- Hosted model only with approved data pack and secrets outside repo.

Exit gate:

- AI summaries are accurate enough to support human review, not automated decisions.

## Phase 5 - Write-back Queue After Read Side Is Stable

Goal: prepare a controlled future path without writing directly to AutoCount tables.

Do not start this phase until:

- read-only extraction has been stable for at least one month,
- dashboards reconcile with AutoCount reports,
- security guardrails are signed off,
- finance/operations define approval rules,
- official docs, local sandbox testing, and optional later vendor review confirm the official write path.

Design:

- Create a queue in the reporting database, not AutoCount production:
  - `queue.writeback_request`,
  - `queue.writeback_request_line`,
  - `queue.writeback_approval`,
  - `queue.writeback_execution_log`.
- Store proposed actions only, such as "create PO draft" or "update item mapping".
- Require human approval before execution.
- Execute only through official AutoCount API, plug-in flow, or approved import template.
- Never update AutoCount SQL production tables directly.

Exit gate:

- A test/sandbox write-back proves auditability, rollback, and human approval before any production use.
